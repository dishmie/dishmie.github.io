MySQL 数据恢复

一、背景

2025年2月1日下午，在线OJ系统，托管在一台 Linux 服务器上，MySQL 运行在 Docker 容器中。当天15:39:58至16:13:00之间，由于一个应用程序的缺陷，online 库中某篇文章及其所有评论被删除。

幸好，我的数据备份策略还算完整：

  • 全量备份：_60_205_254_145-2025_01_22_11_45_26-dump（1月22日的 mysqldump 文件）
  • 二进制日志（binlog）：保留着从全量备份之后至今的所有日志，包括 binlog.000003

只要能拿到全量备份之后、删除操作之前的增量数据，就能把丢失的文章与评论“拼”回来。

二、恢复思路

  1. 查看 binlog 内容，定位到删除文章及评论的时间段。
  2. 使用 mysqlbinlog 工具，按时间范围过滤出 online 库的变更，找到对应的 DELETE 语句位置。
  3. 确定精确的 binlog 位置（position）后，换个思路：直接从 binlog 中提取出更早的 WRITE_ROWS 事件，也就是当初插入文章和评论的 SQL。
  4. 把提取出的 SQL 应用到恢复用的表里，完成数据恢复。

经过排查，当初插入那篇文章及相关评论的操作，恰好集中在 binlog 的位置 7254338 ～ 7257473 之间。接下来的工作就清晰了。

三、环境与路径说明

本机是 Windows，安装了 MySQL 客户端工具 mysqlbinlog.exe，需要分析的 binlog 文件已从服务器复制到本地：

  • 源 binlog 文件：d:\yangbalu\cao\sql\binlog.000003
  • 全量备份文件：d:\yangbalu\cao\sql\poj\_60_205_254_145-2025_01_22_11_45_26-dump
  • 恢复目标目录：
    • 文章数据：d:\yangbalu\cao\sql\poj\article3
    • 评论数据：d:\yangbalu\cao\sql\poj\article_comments

这两个目录下存放的是重建表结构的 SQL 文件，最终恢复出的数据也要写回这些表。

第一次尝试直接在 Docker 容器里执行 mysqlbinlog 查看日志：

docker exec mysql mysqlbinlog /root/mysql/data/binlog.000003

但考虑到后续需要精细过滤和输出 SQL 文件，最终还是把 binlog 拉到本地，用 Windows 版 mysqlbinlog 操作。

四、从 binlog 中提取数据

4.1 第一步：按时间范围初探

先用时间范围看看这段时间内发生了什么（命令在 Windows 命令行中执行，路径需加引号）：

mysqlbinlog --no-defaults --database=online ^
  --start-datetime="2025-02-01 15:39:58" ^
  --stop-datetime="2025-02-01 16:13:00" ^
  "d:\yangbalu\cao\sql\binlog.000003"

输出中能看到多条 DELETE 语句，确认了丢失的数据就是在这段时间被删掉的。但我们的目标是找到删除之前的插入，所以需要更早的位置。

4.2 第二步：定位插入操作的准确位置

通过分析更早时间段的 binlog 内容，最终定位到当初写入那篇文章及其评论的 binlog position 范围是 7254338 ~ 7257473。于是使用 --base64-output=DECODE-ROWS 和 -v 参数，将 ROW 模式的事件解码为可读的 SQL 伪语句，并重定向到 article.sql：

mysqlbinlog --no-defaults --base64-output=DECODE-ROWS -v ^
  --start-position=7254338 --stop-position=7257473 ^
  --database=online ^
  "d:\yangbalu\cao\sql\binlog.000003" > article.sql

生成的 article.sql 文件中，虽然不包含真实的可执行 SQL，但清晰展示了每一行的数据变更：

  • ### insert into online.article ...
  • ### insert into online.article_comments ...

这些注释里包含了完整的字段值，例如文章标题、正文、评论内容、时间戳等。

4.3 第三步：手工拼装可执行的 insert 语句

因为 -v 输出的只是注释形式的伪 SQL，不能直接导入 MySQL，所以下一步就是根据这些信息手工（或借助脚本）拼装出标准的 SQL。我从 article.sql 中提取出了类似如下的数据：

在本地测试环境（或直接连线上库前先在测试库验证）执行：

mysql -u root -p online < recovery.sql
